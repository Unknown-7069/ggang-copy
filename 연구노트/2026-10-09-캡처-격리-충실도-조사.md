# 캡처 미리보기 격리 · 촬영 충실도 조사 (2026-10-09)

작성: 클로드(Fable 5.1 세션). 대상: 깡갤 복사기 `작업본-무팝업복사/capture.js` 의 캡처(미리보기 iframe + 상태창 스냅샷 iframe + modern-screenshot 렌더).
검증 환경: 유저 폰(갤럭시, Termux SillyTavern 1.19.0 'release', Android Chrome 154), adb 무선 디버깅 + CDP `Runtime.evaluate`.
모든 실측은 **합성 iframe/문서** 또는 **유저가 지정한 테스트 방**에서만 했고, 채팅 본문은 열람·출력하지 않았다(수치만).

결론 먼저:
1. 완전 격리(불투명 출처 샌드박스)는 **구현 가능하지만 보류**. 확률·실효성이 낮다고 유저가 판단함.
2. 촬영이 "그대로" 안 찍히는 경우 중 흔한 건 **외부 이미지(호스트가 CORS 미허용)** 하나뿐 → 2026-10-09 밤 `fetchFn` 폴백(직접 → 실리 CORS 프록시 → 회색 자리 + 안내 토스트)으로 보완함.
3. 현재 상태: 상태창 스냅샷 iframe 에 **격리 프렐류드**(`ISOLATION_PRELUDE`, `injectIsolation`) 적용. `parent`→자기 자신, postMessage 무력화, fetch/XHR/WebSocket/EventSource/sendBeacon 차단, CSP `connect-src 'none'; form-action 'none'`, localStorage/sessionStorage/indexedDB/cookie 차단. **`window.top` 만 못 막는다**(브라우저가 덮어쓰기 금지).

---

## 1. 왜 조사했나

- 유저 요구: "캡처 뜬 순간부터 미리보기는 우리 가시성에만 영향 주는 평행세계처럼 아예 격리돼야 한다. 요즘 시뮬레이션 봇은 스크립트·정규식이 채팅 내용이나 변수에 연동돼 있다."
- 동시에: "유저가 둔 시각 상태(숨김·접기) 그대로 담겨야 하고, 상호작용 가능한 상태로 담겼다면 열고 펼친 채로 캡처할 수도 있어야 한다(실효성은 낮아 보임)."
- 미리보기 구조(현행): 메인 미리보기 iframe(같은 출처, 우리가 `doc.write` 로 만든 문서, 실리 스타일시트·html/body 클래스·`#sheld>#chat` 복제) 안에 메시지 복제본을 넣고, 메시지 안 상태창 iframe 은 라이브 문서의 "지금 그려진 DOM"을 직렬화해 `srcdoc` 로 넣는다(`snapshotIframes`). 복사/저장 때만 modern-screenshot 으로 이미지를 만든다.

## 2. 브라우저 사실 (폰 Chrome 154 에서 직접 확인)

| 항목 | 결과 |
|---|---|
| `window.parent` 재정의 | 가능 (`Object.defineProperty`). 프렐류드로 자기 자신을 돌려주게 함 |
| `window.top` 재정의 | **불가** (unforgeable, 같은 출처 문서에서는 절대 못 막음) |
| `sandbox="allow-same-origin"`(스크립트 없음) | 스크립트 0, 부모가 `contentDocument` 접근 가능, 부모가 단 리스너 동작, MO/RO 높이 자동 맞춤 동작(315→415→315 확인) |
| `sandbox="allow-scripts"`(불투명 출처) | 안쪽에서 `top.document`/`parent.document`/`localStorage`/`top.location` 전부 `SecurityError`, `window.open` 은 조용히 무시. 남는 건 `postMessage`(데이터만) |
| 불투명 샌드박스 안의 **중첩** srcdoc iframe | **또 다른** 불투명 출처를 받음 → "우리 래퍼 W(불투명) 안에 봇 문서 S" 구조는 W 가 S 의 DOM 에 접근 못 해 **불가**. 에이전트는 봇 문서 자체(같은 realm)에 있어야 함 |
| 실리 서버 정적 응답 헤더 | `Cross-Origin-Resource-Policy: same-origin`, `Cross-Origin-Opener-Policy: same-origin`, `X-Frame-Options: SAMEORIGIN`, `Vary: Origin`(CORS 는 허용) |
| 불투명 문서에서 실리 자원 | `<img src=실리>` **실패**(CORP), `<img crossorigin="anonymous">` 성공, `fetch` 성공(type cors), `<link rel=stylesheet crossorigin>` 성공(1457 rules), FontAwesome 폰트(CORS 요청) 성공, 외부 이미지는 crossorigin 없이 성공, `data:` 성공. CSS `url()` 배경의 실리 이미지는 no-cors 라 막힘 → 스냅샷 때 data URL 인라인 필요 |
| 불투명 문서의 `fetch('/scripts/...')` | 200 성공 → 격리하려면 CSP `connect-src 'none'` 필수(현재 프렐류드에 있음) |
| top 창의 `message` 리스너 순서 | 나중에 등록한 **캡처 단계** 리스너가 먼저 등록된 비캡처 리스너를 **못 막음**(등록 순서 우선, `stopImmediatePropagation` 무효). `top.postMessage` 는 수신 측 검증에 맡겨야 하는 잔여 채널 |
| srcdoc 의 base URL | 샌드박스여도 부모 문서 base 상속(`baseURI` = 실리 origin) |
| 안쪽에서 높이 측정 | `html.style.height=0` 후 body 자식 bottom 최대값은 맞지만 `scrollHeight` 는 viewport(iframe 높이) 아래로 안 내려감 → 후손 bottom 최대값을 쓰고 scrollHeight 는 폴백만 |

## 3. 실리 생태계 top/parent 사용 실태

### 3-1. 유저 폰 (실측)
- 상태창은 전부 **JS-Slash-Runner(酒馆助手, TH-render, v4.11.3)** iframe. srcdoc/blob iframe 에 **sandbox 속성 없음**(실리와 같은 출처).
- JSR 이 iframe 안에 주입하는 것: `window.$ = window.parent.$`, `window._ = window.parent._`, `_.pick(window.parent, ['EjsTemplate','TavernHelper','YAML','showdown','toastr','z'])` 를 iframe 전역으로 병합, TavernHelper 의 함수들을 전역에 복사(**함수는 부모에 바인딩 → 호출하면 진짜 채팅·변수가 바뀐다**), `window.SillyTavern` 은 `window.parent.SillyTavern` 을 읽는 getter(`getContext` 에 `writeExtensionField` 추가), `iframeId = window.frameElement?.id || window.name`, 높이는 안쪽에서 `frameElement.style.height` 로 직접 설정.
- JSR 은 `window.parent` 를 **Proxy 로 가로채고**(`parent/window/self/top/globalThis` 속성은 프록시 자신, `$`/`jQuery` 는 추적용 커스텀 jQuery, `document` 는 createElement 를 감싼 프록시 — 목적은 iframe 이 부모 DOM 에 만든 요소를 `data-th-iframe-id` 로 표시해 pagehide 때 청소), **`window.top` 도 같은 프록시로 바꾸려 시도**한다. 번들 주석: "window.top 在部分浏览器/Electron 环境中受安全限制，无法被重定义" → 크롬에서는 실패하고 parent 만 성공. 즉 JSR 자체가 "카드 스크립트가 top 을 쓸 수 있다"는 전제로 설계됨.
- 설치된 서드파티 확장 12개(AutoPic, AutoRetry, CPI, Direction-Manager(-Lite), Font-Manager, GCM, JS-Slash-Runner, MultiCast-TTS, PerformanceOptimizer, Pre-fill, Prompt-Quick-Manager) 중 `window.top` 사용은 JSR 뿐(3곳, 위 하이재킹).
- 유저 테스트 방 봇의 인라인 스크립트(2.6~5.3KB×6)에는 `window.top`/`window.parent`/`frameElement`/`TavernHelper` 토큰 **0개** — 주입된 전역 함수만 호출.

### 3-2. 공개 코드 (GitHub / Sourcegraph, 2026-10-09)
- [flizzywine/dsh-tavern](https://github.com/flizzywine/dsh-tavern) 오프닝 스크립트 문서: `window.top.SillyTavern.getContext().extensionSettings.EjsTemplate`, `window.top.TavernHelper.getWorldbook/updateWorldbookWith`, `SillyTavern.chat[0].swipe_id/mes` 직접 수정 + `saveChat()` + `reloadCurrentChat()`. 격리 iframe 에서는 메시지 브리지로만 접근하게 만드는 중.
- [hewzhew/dsh-agent-rp](https://github.com/hewzhew/dsh-agent-rp) 테스트: 카드 코드 `top.SillyTavern.getContext()`, `window[key] || window.parent?.[key] || window.top?.[key]` 폴백, `window.parent.document.querySelector('#send_textarea')`. 이 프로젝트는 컴파일러로 parent/top 접근을 facade 로 재작성하고 `allow-scripts`(top-navigation/popups/forms 제외) 샌드박스 + `event.source` 검증 메시지 브리지로 격리.
- [haide-D/SillyTavern-EchoCore](https://github.com/haide-D/SillyTavern-EchoCore) `frontend/js/dom_parser.js`: iframe 에서 `window.top.postMessage({type:'play_tts', ...}, '*')` — 미리보기에서 누르면 진짜 실리가 TTS 를 재생하는 식의 누출 예.
- 대다수는 `window.parent`: [SenriYuki/SillyTavern-Horae](https://github.com/SenriYuki/SillyTavern-Horae)(`window.parent.SillyTavern?.getContext?.()`, `window.parent.Horae`, `window.parent.getAllVariables`), [weidu12123/Liyuan](https://github.com/weidu12123/Liyuan) `tavernShim.ts`(`window.parent.TavernHelper`), [Civinar-Riley/SillyTavern-AntiNarrow](https://github.com/Civinar-Riley/SillyTavern-AntiNarrow)(`window.parent.document` 로 스타일 주입), [maoyao253/tavern-helper-lite](https://github.com/maoyao253/tavern-helper-lite)(iframe 에 allow-scripts 만 주고 allow-same-origin 은 안 줌 — "공식 조수는 DOM 을 직접 건다"고 설명).
- 테마·정규식 자체는 top 을 안 건드린다: 정규식은 HTML 치환, 스크립트는 실리가 DOMPurify 로 제거 → 실행은 JSR 류 iframe 렌더러에서만.
- 참고: [JS-Slash-Runner](https://github.com/n0vi028/JS-Slash-Runner) · [TavernHelper 문서](https://n0vi028.github.io/JS-Slash-Runner-Doc/) (문서는 전역 `SillyTavern`/`TavernHelper` 만 설명하고 iframe↔호스트 전송 방식은 적지 않음).

### 3-3. 시사점
- 현재 프렐류드(parent→자기 자신)만으로도 JSR 주입 스크립트는 `window.parent.$` 에서 죽어 **상호작용은 이미 대부분 죽고 DOM 스냅샷만 남는다**(= 아래 모드 A 와 겉보기 동일). 남는 구멍은 top 을 쓰는 소수 카드와 `top.postMessage`.
- JSR API 기반 상호작용(변수·채팅 조작)은 애초에 미리보기에서 돌면 안 되는 것. "열고 펼치기"가 되는 창은 순수 DOM 토글만 있는 창뿐.

## 4. 완전 격리 설계안 (보류, 미구현)

### 모드 A — 스냅샷 inert (기본값 후보)
- 스냅샷 iframe 에 `sandbox="allow-same-origin"`. 스크립트 0 → 바깥에 닿을 방법 자체가 없음. 유저가 둔 시각 상태 그대로.
- 부모 쪽 코드(`attachAutoHeight`, `installKindLongPress`, `inlineIframes` 렌더)는 **그대로** 동작(2026-10-09 폰 검증: 높이 81/315, 부모 리스너 발화, MO/RO 높이 동기 315→415→315, 렌더 정상, 잔재 0).
- 한 줄 변경: `snapshotIframes` 에서 `cl[i].setAttribute('sandbox', 'allow-same-origin')`. 2026-10-09 한 번 적용했다가 "상호작용 유지" 요청으로 되돌렸고, 이후 유저가 격리를 보류하면서 현재는 **프렐류드 방식**이 남아 있다.
- 잃는 것: 미리보기 안 JS 조작(접기 버튼 등). 캔버스 픽셀은 어느 모드든 직렬화에 안 담기므로 스냅샷 때 `<canvas>`→`<img data:>` 변환을 추가하면 좋다.

### 모드 B — 불투명 샌드박스 + 에이전트 + R 렌더 (옵션 "미리보기에서 상태창 조작 허용", 기본 OFF)
- S = 봇 스냅샷 문서, `sandbox="allow-scripts"`(allow-same-origin 없음). 안쪽에 우리 미니 에이전트(`<head>` 맨 앞 인라인): localStorage/cookie shim(스크립트가 죽지 않게), 높이 보고(후손 bottom 최대값, RO/MO), 꾹 누르기 보고(좌표만), `serialize` 요청에 현재 DOM(폼 상태 포함) 반환. 봇 스크립트와 같은 realm 이므로 메시지 위조 가능 → 부모는 `event.source === frame.contentWindow` 검증 + 높이 상한 + 위조해도 자기 프레임만 영향.
- 스냅샷 자원 보정(부모가 라이브 문서를 보며): `<img>`/`<video>`/`<source>` 에 `crossorigin="anonymous"`, `<link rel=stylesheet>` 에 `crossorigin`, `<style>`/inline style/같은 출처 stylesheet 의 `url()` 실리 이미지는 data URL 인라인(캐시), `<canvas>`→`<img>`. 폰트는 CORS 요청이라 그대로 됨. 스크립트가 동적으로 넣는 실리 이미지는 `HTMLImageElement.prototype.src` setter 패치로 crossorigin 선부여(에이전트), 동적 CSS 배경은 포기.
- 렌더: 에이전트 `serialize` → 부모가 같은 출처·스크립트 OFF 임시 프레임 R(`sandbox="allow-same-origin"`, S 와 같은 크기, 미리보기 문서 안 오프스크린)에 넣고 **기존 `inlineIframes` 경로 그대로** 렌더(2026-10-09 폰 검증: 330ms, 이미지·폰트 정상, 샌드박스 잔재 0) → 라이브러리를 봇 문서에 넣을 필요 없음.
- 컨테이너 이동(`movePreview`)은 에이전트 `serialize` 결과로 재스냅샷. 선택지/상태창 분류는 스냅샷 때 라이브 문서에서 계산해 data 속성으로.
- 잔여 채널: `top.postMessage`/`top.frames[i].postMessage`(데이터만; 실리 코어는 안 받고 JSR 류는 source 검증). 이미지 로드로 하는 외부 유출은 라이브 페이지에서도 가능한 것이라 미리보기가 더 열어주는 건 아님.
- 알려진 한계: 로드 때 실리 API(JSR 등)에서 데이터를 받아 그리는 상태창은 모드 B 에서 빈 채로 보일 수 있음(그런 봇은 모드 A 가 정답). 작업량 하루 + 테스트 방 검증.

## 5. 촬영 충실도 실측 (격리와 별개) — 2026-10-09

렌더 방식: DOM → 복제·계산 스타일 인라인 → SVG `foreignObject` → 캔버스 → PNG(modern-screenshot 4.7.0). 미리보기는 브라우저가 라이브 DOM 을 그리고 결과물은 SVG 렌더이므로, **레이아웃·크기**는 미리보기와 같지만 **래스터 단계에서만 생기는 차이**는 미리보기가 못 보여준다.

| 케이스 | 실측 | 판단 |
|---|---|---|
| 외부 이미지, 호스트가 CORS 미허용(naver, daum, github, namu, imgur favicon 경로 모두 blocked) | 라이브러리 fetch 실패 → 자리표시 그림(잉크 비율 0.176 균일) | **흔한 실제 케이스**. 유저 폰은 실리 CORS 프록시(`/proxy/<url>`)가 켜져 있어(200, 5430B) 폴백 시 3/3 들어감(잉크 0.874/0.574/0.558). → `fetchFn` 폴백 구현(§6) |
| 실리 로컬 이미지(`/img`, `/user/images`) | 정상(잉크 1.0) | 문제 없음 |
| `backdrop-filter: blur()` 유리 효과 | SVG 렌더에서도 블러 적용(극단값 비율 0.025) | 문제 없음 |
| 글꼴(Pretendard 웹폰트(jsdelivr), serif 계열) | `tagFontsAndLines` 치환 후 폭 차이 ≤1%(201↔199, 228↔226) | 문제 없음. PC 에 설치된 특이 로컬 글꼴은 모양만 조금 다를 수 있음 |
| 교차출처 CSS(jsdelivr Pretendard)의 `cssRules` | 못 읽어 라이브러리가 원격 재요청하다 일부 실패 로그 | 결과 폭엔 영향 없음 |
| 영상·WebGL 캔버스·외부 iframe(유튜브 등) | 빈 칸 | 방식의 한계 |
| 한 메시지 12,000px 초과 | 분할 안 됨 | 드묾 |
| iOS Safari | 미검증(foreignObject+canvas 취약으로 알려짐) | 보고 받으면 그때 |
| 테마/실리 커스텀 | 유저 환경(kkang_phone·접기 스크립트·퀵리플라이 등)에서 라이브 4676 ↔ 미리보기 4677 ↔ 렌더 4677 | `#chat` 바깥 조상 상태에 걸린 테마 규칙만 드물게 어긋날 수 있음 |

## 6. 2026-10-09 밤에 실제로 넣은 것 (capture.js)
- `ISOLATION_PRELUDE` / `injectIsolation`: 스냅샷 srcdoc `<head>` 맨 앞에 CSP 메타 + 격리 스크립트.
